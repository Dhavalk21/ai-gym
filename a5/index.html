Zone 3, Build

Prototyping with AI

Turn an AI idea into a working prototype in an afternoon, keep it safe, and use it to learn, not to ship. Then build one and test it with people.

Lessons

Three short lessons. Each runs the same way: the idea, the framework, a real example, where it breaks, and a quick drill.

1From spec to clickable prototypeFor AI features, a working prototype answers questions a document can't.8 min

The idea

You can write down a button's behaviour. You can't write down an AI feature's behaviour, because the output changes with every input. The fastest way to know whether an AI feature is useful is to use it: real model, realistic inputs, a screen people can touch.

That's now cheap. With vibe-coding tools, a PM can turn a description into a working web app in an afternoon, often without writing code.

The framework

The prototype ladder. Climb only as high as your question needs:

1. Wizard of OzA person writes the "AI" answers by hand. Tests the need.
2. PlaygroundThe real prompt and model on 20 inputs. Tests quality.
3. Clickable appA vibe-coded screen with a real model and sample data. Tests the experience.
4. PilotEngineered, with real data, for a few users. Tests value in daily use.

Start every prototype by writing the one question it must answer.

Real example

In April 2025, Shopify CEO Tobi Lütke made AI use a baseline expectation for all staff in an internal memo he later shared publicly. One rule: the prototype phase of every project should be dominated by AI exploration, because prototypes are for learning and AI speeds that up dramatically.

Source: Lütke's memo, posted on X on 7 April 2025 and reported widely, for example by Digital Commerce 360.

Where it breaks

  • A demo isn't evidence. A prototype that works on your three examples tells you little. Test on messy, realistic inputs.
  • Prototypes create false certainty. Stakeholders see a working screen and assume it's nearly done. Label it clearly.
  • The wrong rung wastes the week. Building an app to test whether anyone needs the feature is slower than a Wizard of Oz test.

2Vibe-coding tools, and where they breakFast to build, easy to ship by mistake.9 min

The idea

Andrej Karpathy named "vibe coding" in a post on 2 February 2025: describing what you want, accepting what the AI writes, and barely looking at the code. By November 2025, Collins Dictionary had made it its word of the year.

Today's tools fall into two groups. App builders (Google AI Studio's Build mode, Lovable, Bolt, v0, Replit) go from a description to a running web app. Coding agents (Cursor, Claude Code and others) work inside a real codebase with an engineer.

The framework

Prototype rules that keep vibe coding safe:

  1. Fake data only. No real customer data, ever.
  2. No real secrets. No production API keys or passwords pasted into the tool.
  3. Private by default. Share links with testers, not the internet.
  4. Labelled. "Prototype, sample data" visible on screen.
  5. Thrown away. Engineers rebuild for production from the learnings.

Simon Willison draws the useful line: vibe coding means building with AI without reviewing the code. That's fine for prototypes and personal tools, not for software other people depend on.

Real example

In 2025, a researcher scanned 1,645 apps from Lovable's public showcase and found 170 of them, about 10%, whose databases anyone could read or write without logging in: names, emails, payment details and API keys. The cause was missing access rules (row-level security) in the generated projects. It was logged as CVE-2025-48757, and Lovable added a security scan to its platform.

Where it breaks

  • Security is invisible in a demo. The app looks finished; the access rules may not exist.
  • Complexity hides. Each new feature makes the generated code harder for the AI, and for people, to change safely.
  • Free tiers have terms. Some tools may use what you type to improve their products. Read them before pasting anything.

Drill: Spot the risk

A colleague's vibe-coded prototype works great, so they want to share the public link with 200 customers using their real invoices. What's the main problem?

3Prototypes for learning, not shippingDecide the question, test with people, keep the knowledge.9 min

The idea

A prototype is an experiment. Its output isn't code, it's an answer: is this useful, can people use it, and do they trust it? Everything you build should serve that answer.

For AI features, three questions matter most: Value (do people want these answers?), Quality (are the answers good on real-looking inputs?) and Trust (do people notice and recover when it's wrong?).

The framework

The one-page prototype brief:

  1. The question: one sentence. "Will freelancers use AI answers about future income to make spending decisions?"
  2. Build, fake, skip: list every part and decide. Build only what the question needs.
  3. Test script: five tasks for five testers, including one where the AI is wrong.
  4. Decision rule: what result means go, change or stop. Write it before testing.
  5. Hand-off: the prompt, the test set and the learnings, not the code.

Real example

An old lesson that still applies: before Zappos built warehouses, founder Nick Swinmurn tested whether people would buy shoes online by photographing shoes in local stores, posting them online, and buying them at full price when an order came in. The back end was entirely faked; the question (will people buy shoes online?) was answered for real (Swinmurn, interviewed by Fortune, 2012).

AI prototypes work the same way: fake everything except the part you're unsure about.

Where it breaks

  • Testing with colleagues tells you what colleagues think. Recruit people who match your users.
  • "Would you use this?" gets polite yeses. Watch what they do, and offer a real choice (a price, a sign-up).
  • Shipping the prototype is the classic trap: it skips security, tests and maintainability.

Key takeaways

  1. For AI features, a working prototype beats a spec. Climb the ladder only as high as your question needs: Wizard of Oz, playground, clickable app, pilot.
  2. Vibe coding is fast and unsafe by default. Fake data, no real secrets, private links, a visible label.
  3. Prototypes are experiments. One question, build only what it needs, test with real users, and decide by a rule you wrote first.
  4. Hand over the knowledge, not the code. The prompt, the test set and the learnings make the real build faster.
