1Tool calling and schemasHow a model asks your code to do things, and why the description matters.8 min

The idea

A model can't look anything up or change anything by itself. With tool calling (also called function calling), you describe tools to the model; when it needs one, it replies with a structured request instead of text. Your code runs the tool and sends the result back, and the model writes its answer.

User asks→Model requests a tool→Your code runs it→Model answers with the result

OpenAI added function calling to its API in 2023, and every major model provider supports it today.

The framework

A tool is described with a schema: a name, a description and typed parameters. For Ledgerly:

{
  "name": "get_open_invoices",
  "description": "Returns unpaid and overdue invoices for one client. Use when the user asks what a client owes or which invoices are open.",
  "parameters": {
    "type": "object",
    "properties": {
      "client_name": { "type": "string", "description": "Client name as written on invoices, e.g. 'Studio Nord'" },
      "status": { "type": "string", "enum": ["unpaid", "overdue", "all"] }
    },
    "required": ["client_name"]
  }
}

Good tool design:

  1. One job per tool, with a name that says it.
  2. A description that says when to use it, like a prompt.
  3. Narrow, typed parameters, with a fixed list of options where you can.
  4. Least privilege: read-only unless writing is the point.
  5. Helpful errors ("client not found, did you mean Studio Nord?") so the model can recover.

Real example

In August 2024, OpenAI made tool calls able to follow a schema strictly ("strict" mode within Structured Outputs), so the requested arguments always match the declared parameters. It applies to every OpenAI model with tool support from the June 2023 versions onward.

Source: OpenAI, "Introducing Structured Outputs in the API", 2024.

Where it breaks

  • The model can pick the wrong tool, or the right tool with wrong arguments. Test tool choice like any other output.
  • Too many tools confuse it. Dozens of overlapping tools make choices worse; group or trim them.
  • A valid call isn't a safe call. Your code must still check permissions: who is asking, and is this allowed?

2The Model Context Protocol (MCP)One standard plug between AI apps and the tools and data they use.9 min

The idea

Before MCP, every AI app needed its own custom integration for every tool: Slack for app A, Slack again for app B. The Model Context Protocol is an open standard that lets any compatible AI app use any compatible tool server, a bit like USB for AI integrations.

Anthropic introduced MCP in November 2024. On 9 December 2025 it donated MCP to the Agentic AI Foundation, a fund under the Linux Foundation co-founded with Block and OpenAI, with support from Google, Microsoft, AWS, Cloudflare and Bloomberg.

The framework

The parts, in plain words:

  • Host: the AI app you use (a desktop assistant, a code editor, your product).
  • Server: a small program that offers tools and data from one system (your files, GitHub, a CRM, Ledgerly's API).
  • What a server offers: tools (actions), resources (data to read) and prompts (ready-made instructions).
  • Local or remote: local servers run on your computer; remote ones run as web services and usually need you to sign in.

For a PM, MCP is a product question too: should your product offer an MCP server, so customers' AI assistants can use it?

Real example

In May 2025, Invariant Labs showed a weakness in agents using the official GitHub MCP server. An attacker wrote hidden instructions into an issue in a public repository. When a user asked their agent to look at that repository's issues, the agent followed the instructions, read the user's private repositories and published their contents in a public pull request. Every tool it used was one the user had approved.

Source: Invariant Labs, "GitHub MCP Exploited", May 2025.

Where it breaks

  • Connecting a server is granting access. Install only servers you trust, and give them the narrowest permissions possible.
  • Tool results are untrusted input. An email, issue or web page fetched by a tool can contain instructions aimed at the model.
  • Approval fatigue: if every action needs a click, people stop reading and click yes.

Drill: Spot the risk

Your agent can read a public support forum and also has write access to your private customer database. What's the risk?

3Workflows vs agentsFive patterns cover most needs. Reach for an agent only when the path can't be known.9 min

The idea

Anthropic's widely cited guide draws a useful line. Workflows are systems where models and tools follow paths you defined in code. Agents are systems where the model decides its own steps and tool use, in a loop, until the task is done.

Its main advice: find the simplest solution possible, and only add complexity when needed. Sometimes that means no agent at all.

The framework

Five workflow patterns (from Anthropic's "Building effective agents"):

Prompt chainingFixed steps, each using the last one's output, with checks between.
RoutingClassify the input, then send it to a specialist prompt or model.
ParallelisationSplit a task into independent parts, or run it several times and vote.
Orchestrator-workersOne model breaks the task down and hands parts to others.
Evaluator-optimiserOne model drafts, another critiques, in a loop.

Then, for agents: label every action act alone (cheap, reversible), ask a person (costly, external or permanent) or never.

Real example

In June 2025, Anthropic described the multi-agent system behind Claude's Research feature: a lead agent plans the research and creates sub-agents that search in parallel. On its internal research eval, this setup beat a single agent by 90.2%. The cost: multi-agent systems used about 15 times the tokens of a normal chat, so Anthropic recommends them for tasks valuable enough to pay for that.

Source: Anthropic, "How we built our multi-agent research system", 2025.

Where it breaks

  • Errors compound. A 95%-reliable step repeated 10 times succeeds far less often. Agents need tests on whole runs, not single steps.
  • Cost and delay grow with every loop. Set budgets and step limits.
  • A dangerous mix: an agent that reads untrusted content, sees private data and can send things out can be tricked into leaking. Remove one of the three (A8 goes deeper).

Cases

One team that used multiple agents where the task justified the cost, and one integration where approved tools became a data leak.

Got it right

Anthropic's research agents

For Claude's Research feature, Anthropic built a lead agent that plans and creates sub-agents to search in parallel, each with its own context, before combining results with citations. On an internal eval it beat a single agent by 90.2%. Anthropic was open about the cost (around 15 times the tokens of a chat) and about where the design doesn't fit: tasks with many dependencies between agents (Anthropic engineering blog, June 2025).

Use agents where the path is unpredictable and the value is high, and be honest about cost.

Got it wrong

The GitHub MCP leak

In May 2025, Invariant Labs showed that a malicious issue in a public GitHub repository could hijack an AI agent connected to GitHub's MCP server. Asked to review the public repo's issues, the agent followed hidden instructions, read the user's private repositories and leaked their contents into a public pull request. The researchers stressed that a server-side patch can't fully fix it; it needs limits on what each agent session can reach.

Every tool you connect widens what injected instructions can do. Scope access per task, and keep a person on outbound actions.

Show a worked example

Job: chase late payments. Design: a prompt chain, not an agent, because the steps are always the same: code finds overdue invoices, the model drafts a reminder using each client's payment history, a person approves, code sends.

Tools: get_open_invoices and get_payment_history (read-only), draft_email (writes a draft). Act alone: read and draft. Ask a person: send anything to a client. Never: change bank details, mark invoices as paid, or follow instructions written inside client emails.

Limits: one draft per invoice per week; stops and flags any invoice with a dispute note for a person.

Key takeaways

  1. Models request tools; your code runs them. Clear names, descriptions and narrow parameters make tools work, and permission checks keep them safe.
  2. MCP is the standard plug between AI apps and tools. Connecting a server grants access, so trust it and scope it.
  3. The simplest design that works wins. Chains, routing, parallel runs and loops cover most needs; agents are for paths you can't predict.
  4. Label every agent action. Act alone, ask a person, or never, and never mix untrusted input, private data and outbound actions without a check.
